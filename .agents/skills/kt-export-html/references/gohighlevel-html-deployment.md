# Deploying custom HTML landing pages to GoHighLevel

Use this note when a self-contained HTML landing page must be published through a HighLevel/GoHighLevel Funnel or Website.

## Recommended hybrid workflow

The lowest-risk workflow is:

```text
local HTML + assets
→ upload local assets to HighLevel Media Storage
→ replace local asset paths with returned public URLs
→ convert the document into a GHL-safe HTML fragment
→ paste the fragment into a blank Funnel/Website page Custom HTML/Code element
→ use native GHL Form/Survey/Calendar embeds
→ save, publish, and verify the live URL
```

Automate asset upload, URL rewriting, packaging, and validation. Keep the final Funnel Builder save/publish step manual unless an official, documented page-write/publish API has been verified for the target account and API version.

## Confirmed Media Storage capability

Official HighLevel API documentation exposes:

```http
POST https://services.leadconnectorhq.com/medias/upload-file
```

Documentation: `https://marketplace.gohighlevel.com/docs/ghl/medias/upload-media-content/index.html`

The documentation states:

- With `hosted=true`, provide `fileUrl`.
- Otherwise provide the uploaded file.
- General file maximum: 25 MB.
- Video maximum: 500 MB.

Related Media Storage APIs cover listing files/folders, creating folders, updating metadata, and deleting/trashing files.

Authentication should use a server-side Private Integration Token for an internal/single-location workflow or OAuth for a distributed Marketplace app. Never place a GHL token in browser HTML or client-side JavaScript.

## Do not overclaim Funnel API support

The public developer portal includes a Funnels category, but research must verify the exact endpoint, schema, scopes, and version before claiming that raw HTML can be written to a page or that a page can be published by API. Absence of an easily discoverable endpoint is not proof that no endpoint exists.

Do not automate against undocumented browser/private endpoints as the default production approach. They may depend on cookies, CSRF state, internal page schemas, and can change without compatibility guarantees.

## Packaging a full HTML document for GHL

A Custom HTML element sits inside a document already generated by GHL. Convert:

```html
<!doctype html>
<html>
<head><style>...</style></head>
<body>...</body>
</html>
```

into a fragment such as:

```html
<style>
  #lp-app, #lp-app * { box-sizing: border-box; }
  /* page CSS scoped under #lp-app where practical */
</style>

<div id="lp-app">
  <!-- page body -->
</div>

<script>
  // page behavior
</script>
```

Guidelines:

1. Remove `doctype`, `html`, `head`, and `body` wrappers.
2. Scope selectors beneath a unique root to reduce collisions with GHL builder styles.
3. Avoid destructive global resets.
4. Rewrite `src`, `srcset`, CSS `url(...)`, video/source URLs, and local font URLs.
5. Preserve accessibility, responsive behavior, and `prefers-reduced-motion` handling.
6. Test sticky elements, overlays, popups, animation, and mobile layout inside the actual published GHL wrapper.

## Shadow DOM packaging for collision-resistant embeds

When a large custom section includes its own hero, carousel, modal, and typography, a Shadow DOM wrapper is a proven way to isolate it from Funnel Builder CSS:

```html
<link rel="stylesheet" href="https://fonts.googleapis.com/...">
<div id="brand-app"></div>
<template id="brand-template">
  <style>:host { display:block; } /* component CSS */</style>
  <!-- component markup, including dialog if used -->
</template>
<script>
(() => {
  const host = document.getElementById('brand-app');
  const template = document.getElementById('brand-template');
  if (!host || !template || host.shadowRoot) return;
  const root = host.attachShadow({ mode: 'open' });
  root.append(template.content.cloneNode(true));
  // Query component nodes through root.querySelector(...), not document.
})();
</script>
```

Important details:

1. Convert document selectors such as `:root`, `html`, and `body` into `:host` rules. Do not leave global resets inside the fragment.
2. Initialize from one guarded IIFE. `host.shadowRoot` prevents duplicate setup when a builder re-evaluates the code.
3. Replace every component query with `root.querySelector(...)` / `root.querySelectorAll(...)`. Document-level event and media APIs may remain global where appropriate.
4. Native `<dialog>` works inside an open shadow root in modern Chromium browsers; test backdrop, Escape, outside click, focus return, and mobile height in the actual published GHL page.
5. Use namespaced public test handles such as `window.brandCarousel`, not generic globals.
6. Verify that the target GHL Custom HTML element preserves `<template>`, `<script>`, Shadow DOM, and inline data URIs. If the builder sanitizes them, fall back to scoped selectors under a unique root ID.

### Assets that exist only as processed local files

If a required processed asset is not hosted publicly - for example, a laptop PNG whose LCD opening was cut to real alpha - either upload that exact processed file to HighLevel Media Storage or embed it as a `data:` URI. Embedding is useful for a small number of critical PNGs and makes the fragment immediately portable, but it increases the HTML size. Keep large backgrounds and slide collections on absolute CDN URLs.

Do not silently substitute the original CDN asset when the local processed asset has materially different alpha, cropping, or composition.

### Deterministic fragment verification

Before delivery, verify the generated artifact rather than only the source page:

- No `doctype`, `html`, `head`, or `body` wrappers.
- No `assets/`, drive-letter, localhost, or relative media references.
- Expected public URL count and any intended `data:image/...` payload.
- Shadow root created exactly once.
- Hero title, processed mockup, slide count, dot count, and Next state change.
- CTA opens the popup and the expected form fields exist.
- Mobile `scrollWidth === innerWidth`; hero and CTA remain inside the first viewport when that is part of the brief.
- Render the fragment inside a neutral wrapper page that imitates a GHL container, then inspect desktop and mobile screenshots.

Keep the original local source untouched when the user asks for a separate deployment artifact. Generate the GHL fragment into a new file and test that new file independently.

## CRM forms

A plain custom HTML form does not automatically become a GHL CRM form. Prefer a native GHL Form, Survey, or Calendar embed so contacts, custom fields, attribution, and workflows behave normally.

If a fully custom form is required, submit it to a trusted backend that calls GHL APIs. Never call authenticated GHL endpoints directly from frontend JavaScript.

## Suggested deploy artifact

A reusable packaging tool can output:

```text
dist/
├── ghl-ready.html
├── asset-manifest.json
├── deployment-report.md
└── original-backup.html
```

Validation should flag remaining local paths, broken public asset URLs, duplicate IDs, unconnected forms, unsupported document-level tags, and script assumptions that conflict with the GHL page wrapper.

## Alternative hosting decisions

- **GHL Custom HTML:** best default when the page must live in Funnel Builder and use native CRM components.
- **External hosting + native GHL embeds/API:** best for Git-based deployments, versioning, rollback, and complex frontend behavior.
- **Iframe inside GHL:** use only when necessary; verify SEO, dynamic height, cross-origin tracking, scrolling, sticky UI, and form attribution before production.
